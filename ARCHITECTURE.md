## Путь данных

```
Postgres (пары/подписчики) --читает--> Parser (ScrapingDog)
Parser --пишет результаты--> Google Sheets (Current/History)
Parser --отчёты--> Telegram
Google Sheets --читает всё--> Sync (sync_sheets_to_db.py)
Sync --пишет snapshots--> Postgres   [замыкает цикл]

Postgres <--читает и управляет--> Dashboard (dashboard_db.py / app.py)
  Dashboard --пишет расписание--> schedule (вкладка «Сбор и управление», блок «Автосбор»; управление открыто всем, у кого есть ссылка, если не задан TEAM_PASSWORD)
  Dashboard --пишет пары ASIN--> competitor_pairs + pair_changes (вкладка «Пары конкурентов»)
  Dashboard --кнопка «Собрать сейчас»--> GitHub API workflow_dispatch --> collect.yml --> защита 2А --> сбор
  Dashboard --«Точечная проверка»--> ScrapingDog напрямую (результат только на экране, в базу не пишется)
```

Ключевой момент: Postgres — одновременно источник (пары, подписчики) и конечная точка (snapshots). Google Sheets остаётся посередине цикла результатов — туда парсер пишет результаты и считает дельты BSR, а синк потом тянет их обратно в базу отдельным шагом. С этапа 4 пары в цикле ведёт только база (лист Competitors парсер не читает).

## Логика "пора ли собирать" — этап 2А (локальная реализация, не live)

Реализация: `db_runs.py`, `should_collect_now.py`, `run_parser_and_sync.py`, `.github/workflows/collect.yml`. Для существующей БД подготовлен `migrations/001_collection_admission.sql`; `schema.sql` содержит новые поля для новой установки. Конкуренция проверена на настоящем PostgreSQL (см. ниже).

1. **`force` живёт внутри gate, не снаружи.** `collect.yml` проверяет только `should_run == 'true'` — единое условие для cron и ручного запуска. Никакого обхода gate через `OR force`. Чекбокс `force` по умолчанию выключен; передаётся как `FORCE_COLLECTION` и снимает только дневной лимит попыток. Не обходит расписание, успешный сбор за сегодня, незавершённую попытку, регистрацию или сбой БД. Локальный force не поддерживается. Ручной запуск больше не означает безусловный немедленный сбор — это намеренное изменение.

2. **Никакого автоматического "устарела по возрасту — можно повторить".** Любая запись `running` (parser или sync, независимо от возраста, включая начатые до полуночи) блокирует новый допуск. Разрешение до использования тоже имеет `status='running'`, но `claimed_at IS NULL`. Разбор зависших попыток — отдельная будущая задача: отменённый workflow или неоднозначный результат COMMIT может остановить сбор до проверки оператором, даже если платный запрос не состоялся.

3. **Явно сохраняем правило "сегодня уже был успешный сбор — не повторяем".** Счётчик попыток за день учитывает ВСЕ статусы (`running`, `error`, `done`), не только running+error. "Есть `done` за сегодня → обычный сбор не запускаем" — отдельная явная проверка, не побочный эффект счётчика.

4. **`run_id` подтверждается и одноразовый (уточнено).** Обёртка (`run_parser_and_sync.py`), получив `COLLECTION_RUN_ID`, не просто читает статус, а сама выполняет единственное разрешённое использование этого пропуска одним запросом:
   `UPDATE collection_runs SET claimed_at = clock_timestamp() WHERE id = %s AND step = 'parser' AND status = 'running' AND claimed_at IS NULL AND finished_at IS NULL AND source = %s AND owner_key = %s RETURNING id`.
   Если запрос не вернул строку или COMMIT не подтверждён — платный шаг не стартует. `owner_key` привязывает пропуск к репозиторию, `GITHUB_RUN_ID` и `GITHUB_RUN_ATTEMPT`; один ID нельзя использовать повторно или передать другому workflow. Проверки «ID сегодняшний» нет: разрешение может перейти через полночь. В GitHub Actions отсутствие ID — ошибка, не самостоятельный повторный допуск. Локально обёртка получает своё разрешение через тот же механизм, с уникальным владельцем; чужой внешний ID не принимает.

5. **Допуск — одна транзакция под общей блокировкой.** На явном `READ COMMITTED` сначала отдельный запрос `pg_advisory_xact_lock(782143, 1)`, затем отдельные запросы чтения расписания, незавершённых попыток и дневного счётчика, затем INSERT. Все пути допуска используют этот ключ. Чтение после блокировки получает свежий снимок, а разрешение возвращается только после подтверждённого COMMIT. Получить `RETURNING id` недостаточно. Транзакция не остаётся открытой во время парсинга; заданы короткие таймауты подключения/запроса/ожидания блокировки.

6. **День и расписание — Europe/Kyiv.** Текущее время берётся из БД через `clock_timestamp()` после получения блокировки, а не через `now()` до ожидания. Счётчик учитывает все строки `step='parser'` с киевской датой `started_at`, без фильтра по статусу; успешность проверяется отдельно. Регистрация фиксирует то же время. Дата незавершённой попытки не ограничивается.

7. **Ошибки учёта больше не проглатываются.** Сбой допуска даёт `should_run=false` и ненулевой exit code; штатный пропуск даёт код 0. Сбой записи завершения не превращается в успех. Для непрерывной защиты запись sync создаётся до закрытия parser: между этапами не остаётся окна без `running`. При неожиданной ошибке запись не освобождается автоматически. **После ненулевого кода парсера синк не запускается** (как было исходно): у пар, обработанных наполовину (только наш ASIN или только конкурент), в Current уже стоит сегодняшняя дата при пустых значениях второй стороны (полностью необработанные пары даты не получают и синком пропускаются), а `sync_snapshots` перезаписывает строки безусловно — синк записал бы неполную строку поверх хороших данных, и «Текущее состояние» показало бы её вместо вчерашней полной. Неполный прогресс остаётся в Sheets до ближайшего успешного сбора; попытка закрывается как `error`, следующий допуск возможен (лимит 3 в день).

```
cron ИЛИ ручной (force=false/true)
  -> gate (всегда, для обоих путей одинаково; день считается по Europe/Kyiv)
       -> короткая транзакция: общий lock -> свежие проверки
          (running любого возраста, done сегодня, расписание, лимит 3)
          -> отказ: пропуск / ошибка БД, никаких платных запросов
          -> допуск: INSERT -> подтверждённый COMMIT -> should_run=true, run_id
       -> обёртка: условный claim по ID + владельцу -> подтверждённый COMMIT
          -> parser -> код != 0: закрыть parser как error, синк не запускать
          -> parser ок: зарегистрировать sync -> закрыть parser (done) -> sync -> закрыть sync

[этап 2Б, отдельно от 2А]
  parser done сегодня, sync — нет -> mode=sync_only -> повтор только синка, без нового ScrapingDog
```

## Тесты для этапа 2А

Изолированные (моки, без реальной БД/Sheets/ScrapingDog):

- (0/1/2 попытки) → разрешить; (3 попытки) → запретить.
- `force=true` + недоступная БД → всё равно `should_run=false`.
- Сбой при регистрации попытки (симулированное исключение) → `should_run=false`.
- Незавершённая `running` со вчера → блокирует, независимо от возраста.
- `run_id` отсутствует / не существует / уже `done`/`error` → платный шаг не стартует.
- `run_id` уже заявлен (`claimed_at` не пусто), статус всё ещё `running` → платный шаг не стартует (проверка одноразовости отдельно от проверки статуса).
- Счётчик попыток и проверка "done сегодня" считаются по календарной дате Europe/Kyiv: тест подделывает текущее время рядом с полуночью UTC (когда в Киеве уже наступил новый день) и проверяет, что лимит для нового киевского дня открывается корректно.

Результат локальной проверки: **88 изолированных тестов проходят** в `tests/test_collection_admission.py`, `tests/test_run_parser_and_sync.py`, `tests/test_should_collect_now.py`. Проверены ошибки COMMIT после RETURNING, одноразовое использование в обёртке, привязка владельца, порядок SQL-команд, поведение force, коды возврата main() и пропуск синка после сбоя парсера. Реальные соединения и дочерние процессы подменены — конкуренцию эти тесты не доказывают.

**Проверка на настоящем PostgreSQL выполнена** (временный сервер, не боевая БД и не схема в ней; [tools/verify_on_temporary_postgres.py](tools/verify_on_temporary_postgres.py), 50 проверок вместе с расписанием и пользователями). Реальный ScrapingDog/Sheets/Telegram не нужны. Подтверждено:

- 16 одновременных допусков — разрешение получает ровно один, остальные получают отказ, а не ошибку.
- 16 одновременных claim одного `run_id` — успех один; чужой владелец (другой запуск, другая попытка, локальный) пропуск занять не может.
- 3 завершённые неудачные попытки за киевский день — четвёртая обычная блокируется, `force` снимает только лимит; успешный сбор блокирует и `force`; `running` трёхдневной давности (parser и sync) блокирует.
- Граница киевских суток: 00:30 по Киеву сегодня считается, 23:30 вчера — нет. Нет строки расписания или время не наступило — отказ и для `force`.
- Миграция 001 на «старой» таблице: строки не меняются, повтор безопасен; **новый код на немигрированной базе отказывает (не работает без защиты)** — порядок внедрения: сначала миграция, потом публикация.
- Gate-скрипт как в GitHub Actions: первый запуск разрешает и отдаёт `run_id`, второй при `running` отказывает, недоступная база и `force` вне ручного запуска дают ненулевой код и `should_run=false`.

Боевой сервер — PostgreSQL 17.9, `Europe/Kyiv` в нём распознаётся (проверено запросом только на чтение).

## Этап 2 — время сбора и пароль команды (реализовано локально, не опубликовано)

- Блок «Автосбор» (с этапа 5 — на вкладке «⚙ Сбор и управление», раньше была отдельная вкладка «⏰ Автосбор»): виден всем (состояние, следующий запуск, последние запуски из `collection_runs`), менять время может только тот, кто открыл «🔒 Управление».
- Управление (решение владельца 20.09.2026: ссылка на сайт есть только у сотрудников): **по умолчанию открыто всем, у кого есть ссылка**, без пароля и без секретов. Имя (необязательно, по умолчанию «Команда») попадает в журнал изменений; на странице постоянно видна пометка «Управление открыто». Закрыть — задать секрет `TEAM_PASSWORD` (от 8 символов): тогда нужен вход «имя + пароль» (сравнение постоянного времени, не больше 5 неудач за 10 минут на всех). Неверно заданный секрет управление не открывает: слишком короткий пароль или строка внутри секции секретов (так TOML вкладывает всё, что ниже заголовка секции) — управление закрыто с пояснением, а не открыто по ошибке. Google-вход с ролью пароль не требует. Риск открытого режима: любой, кто получит ссылку (сайт «public and searchable»), может менять пары и время; смягчения — лимиты (пачка 200, активных пар до `MAX_ACTIVE_PAIRS`, отключение больше 25 пар только с подтверждением), журнал и возврат отключённых пар.
- Выключатель без новых колонок: **нет строки `schedule.id=1` = автосбор выключен** (так уже ведут себя и живая проверка, и код 2А: «Расписание в базе не задано — пропуск»). Включение — upsert строки, выключение — её удаление. Время хранится в киевском часовом поясе, шаг выбора — 30 минут. Ради самого выключателя проверка сбора не менялась.
- Правила — [schedule_store.py](schedule_store.py) и [access.py](access.py) без Streamlit; общий слой запросов — [dbutil.py](dbutil.py) (текст ошибок драйвера наружу не попадает).
- Проверено: тесты (247 проходят, 3 старых падения в `test_history_dedup.py` не связаны), умышленные поломки пароля/блокировки/сохранения тесты ловят (16 из 16), SQL прогнан на настоящем временном Postgres 16 (схема, миграции 001 и 002, расчёт киевского дня на границе UTC, ограничения таблиц) и на реальных данных боевой базы только на чтение.
- **Найдено при проверке:** GitHub запускает расписание нерегулярно — за последние дни проверки шли раз в 2–5 часов вместо «каждые 30 минут» (20.09: 00:41, 02:57, 07:43, потом до 12:30 ничего). Поэтому сбор на 09:00 реально стартует днём (19.09 — в 13:31). Время в интерфейсе — «не раньше», а не «ровно». Точный запуск даст внешний «будильник», который вызывает `workflow_dispatch` по API; проверку допуска (2А) он пройдёт как обычный запуск.

## Точное время сбора — внешний «будильник» (план; код workflow готов, сервис ещё не заведён)

Расписание GitHub (`schedule`) нерегулярно: за последние дни проверки шли раз в 2–5 часов вместо «каждые 30 минут». Решение — внешний сервис по расписанию (например, cron-job.org, бесплатно), который **каждые 5 минут** вызывает GitHub API `workflow_dispatch` для `collect.yml`; gate сам решает, пора ли собирать. Запасной `schedule` остаётся («11,41 * * * *», вне пиковых минут).

- Обязательное условие: сначала 2А в бою. Без него «ручной» запуск обходит gate и частые вызовы запускали бы платный сбор снова и снова. С 2А повторные вызовы безопасны: пока есть `running`, идёт ожидание; после успешного сбора — отказ; после ошибки — повтор при ближайшем вызове (до 3 в день).
- Дёшево по времени Actions: проверка (`should_collect_now.py`) ставит только `psycopg2-binary` и `python-dotenv`, полный `requirements.txt` — только если сбор разрешён (`collect.yml`).
- **Измерено 21.09.2026 по истории запусков GitHub** (публичные данные API): у нас 25 запусков `schedule` за 3,5 суток — около 7 в сутки вместо 48, промежутки 125–305 минут (в среднем 210). У репозитория Rating Radar (`maximumstores/merino-rating-radar`), где в настройках `*/30` и `*/10`, картина та же: 6–7 запусков в сутки, средний промежуток 3,5–4 часа. Частота записи в cron ни на что не влияет — GitHub пропускает большую часть запусков `schedule`, поэтому учащать cron бесполезно, а тезис «воркер проверяет каждые 30 минут» на деле не выполняется. Запуск через API (`workflow_dispatch`) этому не подвержен.
- Что нужно завести владельцу: аккаунт сервиса-будильника и токен GitHub (fine-grained, только этот репозиторий, право «Actions: Read and write», с истечением). Токен хранится в сервисе-будильнике, не в репозитории.
- Настройка задания в cron-job.org: адрес `https://api.github.com/repos/arseniborulko-bit/parser-not-test/actions/workflows/collect.yml/dispatches`, метод POST, расписание — каждые 5 минут; заголовки `Authorization: Bearer <токен>`, `Accept: application/vnd.github+json`, `Content-Type: application/json`; тело `{"ref":"main"}`. Успех — ответ 204. Проверка допуска (2А) пропускает только один успешный сбор в день и не раньше выбранного времени, поэтому частые вызовы безопасны; тот же токен годится для кнопки «Собрать сейчас» (секрет `GITHUB_DISPATCH_TOKEN`).
- Точность после внедрения: старт в пределах ~5 минут после выбранного времени. Подпись на вкладке «Автосбор» («GitHub запускает проверку нерегулярно…») нужно будет обновить.
- Ещё не сделано: 2Б (`sync_only` — повтор только синка, если сбор прошёл, а синк упал; сейчас данные из Sheets попадут в базу при следующем успешном сборе).

## Этап 4 — пары ASIN ведёт база (реализовано локально, не опубликовано)

**Что меняется в пайплайне** (`PAIR_SOURCE=database`, уже задан в `collect.yml`):
- `sheets._refresh_current_sheet_from_matrix` и `refresh_current_matrix` принимают `pairs`; парсер передаёт пары из базы обоим вызовам. Переданный список (даже пустой) — единственный источник раскладки Current; при пустом списке лист не откатывается на старый блок Матрицы.
- `sync_sheets_to_db.py` при `PAIR_SOURCE=database` пропускает копирование листа Competitors в базу (иначе он затирал бы правки из дашборда). Остальное (History, Current, подписчики) без изменений.
- Названия пар для новых строк подставляет сам сбор: `our_product`/`competitor` в Current заполняются заголовками со ScrapingDog.
- Обратимо: `PAIR_SOURCE=sheets` возвращает прежнее поведение (тогда правки из дашборда будут перезаписаны листом).

**Что делает дашборд** (`pairs_ui.py`, `pairs_store.py`; правки доступны так же, как управление расписанием — см. этап 2):
- Разбор вставленного текста: ASIN вида `B0XXXXXXXX` (так же, как в парсере), ссылки Amazon (страна берётся из домена: com, ca, co.uk, de, fr, es, it, com.mx, co.jp, com.au), запись `ASIN:US`. Неподдерживаемая страна или мусор — «не распознано», а не молчаливое исправление. Повторы в тексте отбрасываются.
- Превью до записи: «Новых / Вернутся / Уже есть / Не подошло», сколько ASIN добавится в каждый сбор, сколько станет активных пар. Конкурент с другого маркетплейса, чем наш товар, и совпадающий с нашим ASIN отбрасываются с пояснением. Пачка — до 200, активных пар — до `MAX_ACTIVE_PAIRS` (по умолчанию 1000; сейчас активно около 620).
- Убрать: пара не удаляется, а получает `active=FALSE` (история снимков остаётся); отключение больше 25 пар требует ввода «УБРАТЬ». Вернуть отключённые — отдельный раздел; повторное добавление отключённой пары тоже возвращает её.
- Каждое изменение и запись в `pair_changes` идут одной командой (транзакцией): кто, что, когда, какая пара. Журнал необязателен: пока таблицы нет (миграция 003 не применена), изменения применяются без записи в журнал (в логах предупреждение, экран журнала это объясняет), а после миграции журнал подключается сам. Права проверяются в самих функциях записи, не только скрытием кнопок.
- «Текущее состояние» показывает только активные пары (`JOIN competitor_pairs … active`), список пар подставляет пустые названия из последнего снимка.

**Проверено:** 358 тестов (из умышленных поломок новой логики пойманы все: 20 на пары и пайплайн, 10 на открытое/закрытое управление, 5 на журнал), SQL на настоящем временном Postgres 16 (74 проверки в `tools/verify_on_temporary_postgres.py`, в т.ч. 12 одновременных добавлений одной пары → одна строка и одна запись журнала; путь без журнала), превью и загрузка страницы на живых данных боевой базы только на чтение.

**Порядок внедрения** (публикация уже выполнена 20.09.2026 ~15:41; дашборд показывает новую версию после перезапуска Streamlit): 1) миграция 003 (журнал + два индекса, аддитивная; нужно разрешение владельца) — желательна, но пары работают и без неё; 2) по желанию один раз подтянуть пары из листа в базу (если в листе Competitors правили после последнего сбора 20.09 12:52; запись в боевую базу, нужно разрешение); 3) сказать команде: пары теперь ведутся в дашборде, лист Competitors парсер не читает. Лист остаётся для заметок; его колонки «Notes», «Коментарии», «Сабака/Битый» парсер и команда используют как раньше.

## Этап 5 — вкладка «⚙ Сбор и управление» (по образцу Rating Radar; реализовано, публикация за владельцем)

Четыре блока на одной вкладке (`collect_ui.py`; правила без Streamlit — `run_control.py`, `github_dispatch.py`, `spot_check.py`):
- **Запустить сбор.** Сверху сводка «В работе N ASIN: наших X · конкурентов Y (US 273 · CA 202 …)»: считаются только активные пары, ASIN один раз (так же, как парсер, который каждый ASIN запрашивает один раз за сбор). Кнопка «🚀 Собрать сейчас — на серверах GitHub» вызывает GitHub API `workflow_dispatch` для `collect.yml` (тело запроса только `{"ref": "main"}` — без `force`, обходного пути нет). Сам сбор идёт на GitHub, проходит защиту 2А как любой запуск: только после времени по расписанию, один успешный сбор в день, не больше 3 попыток; при закрытых воротах кнопка неактивна и показывает причину (`run_control.admission_preview` — те же правила, что у `db_runs.admit_parser_run`, но только чтение и без `force`; сверка на настоящей базе — 14 проверок в `tools/verify_on_temporary_postgres.py`). При нажатии допуск проверяется заново, после успешной отправки — пауза 2 минуты. Права: открытое управление / пароль / роль — как у остальных действий; проверяются и в обработчике нажатия.
- **Точечная проверка.** До 5 ASIN или ссылок за раз (страна из ссылки, `ASIN:US` или выбранный маркетплейс), по одному запросу ScrapingDog на ASIN, результат — таблица на экране (название, цена, BSR, наличие, оценка, отзывы, категория, бренд); в базу и в Google Sheets ничего не пишется. Каждый ASIN стоит кредит, поэтому расход ограничен на весь сайт: 20 в час и 60 в сутки (счётчик в памяти процесса, перезапуск сайта его обнуляет). Без секрета `SCRAPINGDOG_TOKEN` блок на вкладке не показывается вовсе (ни заголовка, ни подсказки про секрет) и появляется сам, когда токен задан. Ошибки запросов отмечаются по каждому ASIN отдельно, текст ошибки и токен на экран не попадают.
- **Автосбор.** Время и выключатель — прежний блок этапа 2, перенесён сюда.
- **Обновить данные из базы.** Сбрасывает кэш показа (дашборд иначе держит данные до нескольких минут); доступно всем, ничего не пишет.

Секреты Streamlit (необязательные, образец — `.streamlit/secrets.toml.example`; обычные ключи — выше секций):
- `GITHUB_DISPATCH_TOKEN` — fine-grained токен GitHub, только этот репозиторий, право «Actions: Read and write». Без него кнопка неактивна и объясняет, что нужно добавить. Этим же токеном можно позже настроить внешний «будильник» (см. раздел ниже).
- `SCRAPINGDOG_TOKEN` — для точечной проверки.
- `GITHUB_REPO` — только если репозиторий называется иначе (по умолчанию `arseniborulko-bit/parser-not-test`).

Оформление (исправлено 20.09.2026 после жалобы «не вижу вкладку»): страница нарисована светлой (`.stApp { background: #f6f7fb }`), а Streamlit в тёмной теме браузера красит текст в белый — подписи неактивных вкладок, полей и текст кнопки «Скачать…» становились белыми на светлом. Поэтому тема закреплена светлой в `.streamlit/config.toml` (`[theme] base = "light"`). Кроме того, новый Streamlit рисует вкладки не как `<button>`/baseweb, а как `div[role="tab"]` — прежние правила («тёмная вкладка, белый текст, активная синяя») к ним не применялись; теперь вкладки выбираются по `role`. Неактивные кнопки внутри вкладок приглушены (раньше правило «полная непрозрачность» делало их неотличимыми от рабочих). Проверено скриншотами локального сайта в тёмной и светлой теме браузера; `tests/test_dashboard_style.py`.

Не перенесено из Radar намеренно: переключатели «Чайлды/Паренты/Конкуренты» (у нас нет такого деления), сбор из браузера, «Structured API». Проверено: 456 тестов проходят (те же 3 старых падения в `test_history_dedup.py`), умышленные поломки новой логики (22 штуки) и оформления (5 штук) тесты ловят все, боевые данные открыты только на чтение (сводка сходится с базой: 609 ASIN, из них 94 наших), SQL и сверка предпросмотра с настоящей проверкой допуска — на временном Postgres 16 (88 проверок).

## Важная поправка: дашборд — не просто просмотр, а основной пульт управления

Ранее диаграмма (и я, и Кодекс) неверно подписали связь дашборда с базой как "только чтение". Дашборд должен быть основой управления проектом: расписание запуска парсера и управление ASIN/парами конкурентов.

### Переходное состояние

- Google Sheets остаётся местом записи результатов (Current/History): парсер пишет туда, синк переносит в `snapshots`. С этапа 4 (после публикации) пары туда больше не «зеркалятся»: раскладка Current строится из пар базы (`refresh_current_matrix(pairs=…)`), лист Competitors парсер не читает (кроме пометки битых ASIN в существующих строках), синк пары из листа не копирует (`PAIR_SOURCE=database`). До публикации этапа 4 живой код ещё читает пары из листа для раскладки, а синк перезаписывает базу листом — поэтому этап 4 публикуется целиком, а не по частям.
- Дашборд публичный на просмотр (Streamlit Cloud, «public and searchable»); менять расписание и пары может любой, у кого есть ссылка, пока не задан секрет `TEAM_PASSWORD` (тогда — после ввода пароля; либо Google-вход с ролью).

### Конечная система (после отключения Sheets, план)

- Postgres — единственный источник пар/расписания/ASIN. Дашборд пишет туда напрямую, парсер читает оттуда, результаты пишутся в Postgres напрямую (`sheets.py`/`_refresh_current_sheet_from_matrix` переписывается на SQL-эквивалент). Google Sheets не участвует в цикле вообще.

### Согласованная очерёдность (обновлено 20.09.2026)

Решение владельца: пользователи — **команда** (один общий список ASIN и одно расписание). Ориентир по работе — Rating Radar (публичный репозиторий `maximumstores/merino-rating-radar`): пачка ASIN/ссылок с разбором перед записью, галка «Автосбор включён» и время в базе, кнопка «Собрать сейчас» через GitHub API. Входа у Radar нет — здесь он обязателен.

0. Довести до боя защиту платных запусков (2А): код готов и проверен на настоящем временном Postgres. Миграция 001 к боевой базе применена (20.09.2026); осталось опубликовать. После этого — внешний «будильник» для точного времени сбора (см. раздел выше).
1. **Вход и роли (Google)** — реализовано локально, пока не включено: без секции `[auth]` в секретах ничего не меняется. Защиту сейчас даёт общий пароль команды (этап 2).
2. **Время сбора, статус и пароль команды** — реализовано локально, см. раздел ниже. Кнопка «Собрать сейчас» через GitHub API — реализована на этапе 5 (проходит через защиту 2А; «игнорировать лимит» из дашборда не сделан намеренно). Ещё нет: уведомления в Telegram о сбое.
3. Надёжность данных: пустые значения не затирают хорошие при синке; решение по «синк после сбоя парсера».
4. **Пары ASIN** — реализовано локально, см. раздел «Этап 4»: Postgres — главный источник, добавление пачкой с разбором, отключение вместо удаления, журнал изменений, лимит.
5. Прямая запись результатов сбора в Postgres и отключение Google Sheets — финальный этап.

**Управляющие функции (расписание, пары, запуск сбора) включаются в интерфейсе только вместе с проверкой прав доступа — не раньше.** Пока дашборд публичный без авторизации, ни одна пишущая функция не должна быть доступна анонимному посетителю.

## Открытые вопросы (не закрыты ни одним этапом)

- Ошибки, которые сам парсер проглатывает и завершает работу с кодом 0.
- Пустые значения при синке: после сбоя парсера синк теперь не запускается, но `sync_snapshots` по-прежнему безусловно перезаписывает строки; пара, у которой в успешном прогоне не нашлись данные (маркер «@») или обработана только одна сторона, получает сегодняшнюю строку с пустыми значениями. Нужен запрет затирать хорошие значения пустыми (`COALESCE`/пропуск пустых строк).
- Автоматическое восстановление после зависшей `running`-попытки (сейчас — только безусловная блокировка, без разбора).
- 2Б: повтор только синка, если парсер отработал, а синк упал (данные окажутся в базе только при следующем успешном сборе).
- Три старых теста `test_history_dedup.py` падают и без новых правок (в заглушке листа нет `row_count`).
